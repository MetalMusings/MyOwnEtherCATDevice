# EaserCAT 3000 – CiA402 firmware

The EaserCAT 3000 is a four-axis CiA402 stepper drive. It follows ETG.6010 (the CiA402
Implementation Directive) and ETG.1020 (Protocol Enhancements).

* Vendor ID `0xD0BED1D0`, product code `0x3402`, revision 1.
  The product code changed from `0x3000` because the process data are no longer compatible.
* Device type (0x1000 and 0x67FF per axis): `0x00040192`. That is profile 402, stepper drive.
* Four axes in one device. The 0x6000–0x67FF range is shifted 0x800 per axis:
  axis 1 = 0x6xxx, axis 2 = 0x68xx, axis 3 = 0x70xx, axis 4 = 0x78xx.
* Modes: **csp (8)**, **csv (9)** and **homing (6)**, methods 19–22, 35 and 37.
  Supported drive modes (0x6502) = `0x1A0`. The mode can be switched in OP through 0x6060.
* Units: there is no factor group (ETG.6010 table 56). Positions are in steps, velocities
  in steps/s and accelerations in steps/s². The master does the scaling to mm.
* Step/dir outputs from hardware timers, every step placed to 12.5 ns (see "Step
  generation"). The highest step rate of an axis is 1 / (step length + step space),
  0x2010+n:01/:02, up to 500 kHz at the shortest 1 µs + 1 µs.
* Synchronization: DC SYNC0 (recommended), or SM synchronous. The minimum cycle time
  depends on the step rates of the axes: 350 µs with the default timing (see "Choosing
  the cycle time"). The board reports it in 0x1C32:05 and refuses SAFEOP with AL 0x0036
  below it.
* Clock: 160 MHz from the 8 MHz crystal (see "Timing").

## Generated files

`tools/gen_od.py` is the single source of the object dictionary. It generates
`lib/soes-esi/objectlist.c`, `utypes.h`, `ecat_options.h`,
`MetalMusings_EaserCAT_3000_CiA402.xml` (the ESI) and `eeprom.bin` (the SII).

```
python3 tools/gen_od.py
```

Write the new EEPROM after flashing, for example with IgH:
`ethercat sii_write -p <pos> lib/soes-esi/eeprom.bin`.

## Flashing: choosing the board by MCU UID

Several ST-Links can be connected at the same time. Before `pio run -t upload`,
`tools/select_stlink.py` connects to every ST-Link (read only, no halt, no reset) and reads the
96-bit unique id (UID) of the MCU behind it. Only the board whose UID matches `custom_mcu_uid`
in `platformio.ini` is flashed. The UID is burnt into the chip, so it follows the board, not the
USB port or the programmer. The upload output shows what was found and chosen:

```
Val av kort via MCU UID (custom_mcu_uid = 003400165646501220313936):
  ST-Link 1-3.4.1.4    UID 0041003e3238510a32313838
  ST-Link 1-3.4.4.4    UID 003400165646501220313936  <-- matchar
Flashar via ST-Link 1-3.4.4.4 (UID 003400165646501220313936)
```

* **Another board:** run `pio run -t boards` (or an upload, which then stops without flashing),
  copy the board's UID into `custom_mcu_uid`.
* **Once, without editing the file:** `MCU_UID=<uid> pio run -t upload`.
* **Empty `custom_mcu_uid`:** the ST-Link is used if exactly one is connected, otherwise the
  upload stops.
* Linux only. On other systems a warning is printed and the upload runs without the check.
  `pio debug` is not covered.

**Set the max acceleration (0x60C5).** The default 0 keeps the board from limiting the
acceleration: the master's planner (LinuxCNC's `MAX_ACCELERATION`) already does. But
without a limit the step loop may go from rest to full rate in one cycle, so a single late
or repeated frame from the master makes the axis jerk (it can even reverse for a cycle).
With a limit somewhat above the master's (1.5–2 × `MAX_ACCELERATION` × `SCALE`, in
steps/s²) such a frame is hardly seen, and normal motion is not affected.

The board outputs are 0x2105 OR (0x60FE:01 & 0x60FE:02) over all axes. 0x60FD and 0x60FE are
not in the default mapping (the board I/O is in 0x2104/0x2105), but can be mapped.

## Process data

The mapping objects (0x1600–0x1604, 0x1A00–0x1A04) and the assignments (0x1C12, 0x1C13)
can be written in PREOP. The ETG.1020 chapter 10 procedure applies: set SI0 = 0, write the
entries, then set SI0 = n. Each PDO holds up to 8 entries.

| PDO | Default content |
|---|---|
| 0x1600+n | Controlword, Modes of operation, Target position, Target velocity |
| 0x1A00+n | Statusword, Modes of operation display, Position actual, Velocity actual, Following error |
| 0x1604 | Encoder outputs, analog output, digital outputs (0x2105) |
| 0x1A04 | Encoder inputs, frequency input (0x2103), digital inputs (0x2104) |

0x1C32/0x1C33 (SM parameters, ETG.1020):

| Sub | Name | |
|---|---|---|
| :01 | Sync mode | 1 SM synchronous, 2 DC SYNC0 |
| :02 | Cycle time | ns |
| :05 | Minimum cycle time | ns, what the step rates of the four axes allow (each axis at 1 / (step length + space), or at 0x607F if that is lower). 0xFFFFFFFF: too many steps for any cycle time |
| :06 | Calc and copy time | ns, the longest cycle measured |
| :08 | Get cycle time | write 1: new measurement (clears :06, the maxima of 0x2000 and the queue leads of 0x2010+n:08); 2: also the counters :0B, :0C and 0x2010+n:06, :07 |
| :0A | Sync0 cycle time | ns |
| :0B | SM event missed | cycles without new outputs from the master |
| :0C | Cycle time too small | SYNC0 came before the last cycle was done |
| :20 | Sync error | |

0x2000 Cycle diagnostics of the board (read only, can be mapped into a TxPDO):

| Sub | Name | |
|---|---|---|
| :01 / :02 | Step generation load, 0.1 % | the share of the CPU the step interrupts and the planning took in the last cycle / at most |
| :03 / :04 | Cycle time used, 0.1 % | the share of the cycle time the last cycle took / at most. Above about 900 the cycle time is too short |
| :05 | Cycle distance max ns | the longest time between two SYNC0 cycles |
| :06 | Step interrupt time max ns | the longest step timer interrupt |

0x2010..0x2013 :05..:08, step diagnostics of axis 1..4 (read only, can be mapped into a
TxPDO):

| Sub | Name | |
|---|---|---|
| :05 | Max step frequency Hz | the rate the axis is held at: 1 / (:01 + :02), lower if 0x607F is set lower, or if the step queue cannot hold a cycle of it (only long cycles: about 175 kHz at 10 ms) |
| :06 | Frequency limited | 1: the axis was held at :05 (sticky): its command was faster, or it caught up at full rate after a jump of the command. A single late or repeated frame does not set it when an acceleration limit (0x60C5) is set |
| :07 | Late steps | the axis' step queue ran empty while it was moving: steps came late |
| :08 | Step queue lead min µs | the shortest time the queue was ahead when its next part was planned |

What it tells:

* **Cycle time too short:** SAFEOP is refused with AL 0x0036 if the SYNC0 cycle is shorter
  than 0x1C32:05. In OP, 0x2000:04 near 1000, a rising 0x1C32:0C or 0x2010+n:07 means the cycle
  does not fit.
* **Too many steps:** 0x1C32:05 = 0xFFFFFFFF. Longer step timing or 0x607F on the axes that do
  not need the full rate lower it.
* **Speed too high:** 0x2010+n:06 shows that the axis was held at its step rate limit. It then
  lags its command and a following error follows.

## Board I/O

From the schematic and the PCB (`Kicad/`):

| Terminal | Circuit | MCU pin |
|---|---|---|
| IN1..IN4 (J6) | 24 V, TLP292-4 U4 channels 4..1. High = input energized | PE11, PE10, PE9, PE8 |
| IN5..IN8 (J7) | as above, U5 channels 4..1 | PE15, PE14, PE13, PE12 |
| OUT1..OUT4 (J8, J9) | TLP292-4 U3, isolated transistor (n+ collector, n- emitter) | PC5, PB0, PB1, PE7 |
| Encoder (J10) | 5 V, 1k pull-ups. A, B on TIM2, Z on an interrupt | PA0, PA1, PA3 |
| THCAD (J5) | differential input, MAX3485 receiver | PA2 (TIM5 CH3) |
| DAC (J13) | the MCU's DAC directly, 0–3.3 V, no amplifier | PA4 |

0x2104 and 0x60FD show the inputs after the polarity and the filter, so an NC switch reads 1
when it is actuated.

The optocouplers are wired in reverse order within each group of four inputs. The firmware
reads them in terminal order, so bit 0 of 0x2104 is IN1. The firmware before CiA402 read
PE8..PE15 as bit 0..7, which made IN4 bit 0.

**Analog output:** 0..3.3 V straight from the DAC. A spindle drive with a 0–10 V or ±10 V input
needs an external amplifier (gain about 3, plus an offset for ±10 V).

**Frequency input:** TIM5 time-stamps every rising edge, and DMA copies the stamps to a ring
buffer, so there is no interrupt per edge. Each cycle the frequency is the edges since the last
cycle divided by the time between the first and the last of them. That is one 12 ns timer tick
of resolution, at any frequency up to about 1 MHz at a 1 ms cycle. Inputs below 10 Hz read 0.

## Homing and limit switches

Homing works as in IEC 61800-7-201 and the A6/ECT drives. Set 0x6060 = 6, then a rising
edge of controlword bit 4 starts. Statusword bit 10 means stopped (done, not started or
interrupted), bit 12 means homing attained, and bit 13 means homing error.

| Method | Home switch | Home position |
|---|---|---|
| 19 | active on the positive side | the edge where it goes off, moving negative |
| 20 | active on the positive side | the edge where it comes on, moving positive |
| 21 | active on the negative side | the edge where it goes off, moving positive |
| 22 | active on the negative side | the edge where it comes on, moving negative |
| 35, 37 | none | the current position |

The search for the switch runs at 0x6099:01. Every move that ends at the home edge runs
at 0x6099:02, so the edge is always reached slowly and from the same side. If the switch
is already active at the start, the search is skipped. The axis accelerates with 0x609A
and brakes at the switch with the quick stop deceleration 0x6085, as the ECT drives do.

The edge gets the position 0x607C. Every input change interrupts and latches the step
count, so the edge is exact to one step whatever the cycle time. The axis stays where it
stopped, a few steps past the edge, and is not moved back.

These events end homing:

| Event | Result |
|---|---|
| Bit 4 back to 0, or halt (bit 8) | Decelerates with 0x609A. Not homed, no error |
| Leaving "Operation enabled", or another mode | Ends immediately |
| A limit switch during methods 19–22 (as on the A6) | Homing error, stops with 0x6085 |
| The time limit 0x2020+n:04 is exceeded (60 s, as the A6 default) | Homing error, stops with 0x6085 |
| Method 19–22 with a homing speed of 0 | Homing error at once |

A limit switch that is the same input as the home switch is not checked during homing.

After a mode change into csp, the axis follows the target only once the target is within
10 steps of the actual position. This matters most after homing, where the position has
just been re-referenced and a master may still send a target in the old frame for a cycle.

**Limit switches** (0x2020+n:02/03) act in every mode, the same way on the A6
(forward/reverse overtravel) and the ECT (CW/CCW limit):
* Motion towards an active limit stops with 0x6085. In csp the axis holds until the target
  is back on the free side of where it stopped. Motion away from the limit is allowed.
* Statusword bit 11 (internal limit active) is set while a limit is active. It is not a
  fault: the following error supervision is paused while the axis holds.

## Behaviour

* State machine as in ETG.6010 figure 2, including Quick stop active and Fault reaction
  active. Halt (bit 8) is ignored in csp/csv, as the directive requires.
* Following error supervision in csp: 0x6065/0x6066 → fault 0x8611.
* When the ESM leaves OP, every axis that has power enabled reacts according to 0x6007.
  The default (1) is a fault, 0x8100. Axes that the master has already disabled are not affected.
* A missed frame in csp (no new RxPDO at SYNC0) extrapolates the target position for up
  to 3 cycles instead of braking hard. The event is counted in 0x1C32:0B.
* If DC is active in OP and SYNC0 stops, the device goes to SAFEOP+ERROR with AL status
  0x001A (synchronization error).

## Timing

### The clock

The Arduino core's generic F407 setup runs the PLL from the internal 16 MHz RC oscillator
(HSI). On this board's chip that ran 4.8 % slow: 160 MHz instead of 168, measured against
the host's clock (step rates, `micros()`, the THCAD frequency, all timeouts 4.8 % off).
`SystemClock_Config()` in `main.cpp` now runs it from the 8 MHz crystal Y1, at exactly
160 MHz. Not 168 MHz: SPI1 would then run at 42 MHz, and the AX58100 failed about a
quarter of the SDO reads and could stay in INIT (AL 0x0016). At 160 MHz SPI1 runs at 40 MHz,
as before. If the crystal does not start, the HSI setup is used.

### Step generation

Each axis has a timer of its own, in PWM mode with ARR and CCR preloaded (`include/StepTimers.h`):

| Axis | Step | Timer | Dir |
|---|---|---|---|
| 1 | PA11 | TIM1 CH4 | PA12 |
| 2 | PC9 | TIM8 CH4 | PC8 |
| 3 | PD12 | TIM4 CH1 | PD11 |
| 4 | PE5 | TIM9 CH1 | PE4 |

The timers count at 80 MHz (12.5 ns). Every timer period starts with a step pulse (or
none); a short interrupt at each update event loads the next period from the axis'
queue (in the CCM RAM), sets the direction pin and counts the step. Once per cycle the
planner (`src/StepPlanner.cpp`) runs LinuxCNC's position loop (`src/StepGenLoop.cpp`)
from where the queue ends, ramps the velocity at the loop's acceleration limit as the old
DDS did, and puts the steps of the next cycle into the queue, each to the tick. It keeps
the step length, step space, direction setup and hold, and it runs 300 µs ahead of the
cycle; the position command is extrapolated by that much, so the lag behind the command
is the loop's own, as with the DDS (host test: within 5 steps of it). A window boundary
does not move a step: at a constant speed every interval is within a tick of the ideal.
If a cycle comes late and a queue runs empty, the axis waits and the steps come late
(0x2010+n:07); none is lost. When an axis is disabled, its queue is dropped at once.

Before this the steps came from a 10 µs base period interrupt (LinuxCNC's `make_pulses()`):
at most 50 kHz, with the step times rounded to 10 µs, and about half the CPU while moving.

### Choosing the cycle time

Measured in OP, 2026-11-27, with the IgH master and the ecat component, all four axes in
csv at the same rate, 2 µs step length and space (cycle time used, average):

| Cycle | 4 × 45 kHz | 4 × 100 kHz | 4 × 125 kHz | 4 × 150 kHz | 4 × 175 kHz | 4 × 200 kHz |
|---|---|---|---|---|---|---|
| 1 ms | | 39 % | 47 % | 58 % | 71 % | 89 %, one late step |
| 0.5 ms | | 65 % | 76 % | 94 % (99 % at most) | | |
| 0.25 ms | 84 % (10 µs timing) | | | | | |

Every rate came out exact (to 0.1 %), with no late step except where noted. A step costs
about 1.1 µs of CPU: 0.45 µs in the interrupt, the rest in the planning. The model
(`include/CycleModel.h`, 0x1C32:05) is 160 µs per cycle plus 1.1 µs per step, with 20 %
margin; it takes each axis at its highest rate (1 / (step length + space), or 0x607F if
that is lower). It accepts all the cases above but 0.5 ms at 4 × 150 kHz and 1 ms at
4 × 200 kHz. With the default timing (5 µs + 5 µs) on all four axes it asks for 350 µs;
to run faster cycles, set 0x607F to what each axis really needs.

Measured parts (PREOP, before the clock change, so at 160 MHz):

| Part | Time |
|---|---|
| SPI to the AX58100, 75 bytes | 18 µs with DMA. Before: 47 µs with `SPI.transfer()`. |
| PDO pack (75 B) / unpack (54 B) | 8.2 / 5.5 µs. Before: 21.9 / 13.9 µs. |
| Application: 4 axes, step generator update, inputs | about 35 µs. Before: 54 µs with software `double` arithmetic. |
| One cycle in PREOP (0x1C32:06, worst case) | 46 µs. Before: 72 µs. |

How it is done:
* **Step timers:** register level, with their own handlers in a vector table copied to
  RAM, not through HardwareTimer/HAL. The planner has a short loop for the steps after
  the first of a segment: about 50 CPU cycles per step at constant speed.
* **SPI:** transfers of 8 bytes or more use DMA2. Shorter ones use a register loop.
* **PDO packing:** entries that are 8, 16 or 32 bits long and start on a byte are copied
  directly. Other entries take SOES' bit slicing path.
* **No `double` in the cycle:** the F407's FPU is single precision only. Absolute positions
  are 64-bit fixed point: steps with 28 fraction bits, the format of the step generator's
  accumulator. Differences of positions, velocities, accelerations and times are `float`.
  `float` alone would not do: at a million steps its resolution is 0.06 steps, which the
  position loop would turn into velocity noise. LinuxCNC's position loop is in
  `src/StepGenLoop.cpp`. A host test runs it side by side with the original `double`
  version (36000 cycles, moves, jumps, csv, limits, far from zero): they never differ by
  more than one step, and both settle exactly on the target. `Cia402Axis.cpp` and
  `StepGenLoop.cpp` are compiled with `-O2`.

Profiling build: `PLATFORMIO_BUILD_FLAGS=-DCYCLE_PROFILE pio run -e genericSTM32F407VGT6 -t upload`.
It fills the struct `prof` (CPU cycles) every cycle, and every 2 s outside OP with all axes
disabled it also runs benchmarks against the old SPI and PDO paths. `runProf` has the
interrupt and cycle times while running; the debugger zeroes it to start a measurement.
Read them with OpenOCD without halting, for example `mdw <address of prof> 44`. Outside
OP it also times the planner on a queue of its own (`prof.pulses100`: 100 steps at
constant speed, `prof.core400Active`: a ramp).

## Host tests

```
test/host/run_tests.sh
```

These test the state machine, the csp/csv logic, polarity, quick stop, the fault handling and
the generated object dictionary, including the PDO remapping rules. Only gcc/g++ is needed.

The step generation is tested with a simulated timer that runs the queues as the hardware
does: every pulse and direction change against the step timing (length, space, setup,
hold), the step count against the planned position, the intervals at constant speed (within
a tick), late cycles and the flush on disable. A closed loop test runs csp moves through the
position loop, the planner and the timer side by side with the old DDS step generator.
